What changed on 2026-09-19, and what it teaches about ASR

A review of one day's work on mlx-qwen3-asr, written for the maintainer who did not write the code. Three releases (0.4.1, 0.4.2, 0.4.3), eight PRs, four published model artifacts, and one finding that changed a headline feature. The point of this document is not the changelog; it is the concepts behind each change and what they mean for how the project should be run.

If you read only one paragraph

Every metric this project tracked for streaming (partial stability, rewrite rate, finalization delta, latency) was green while the streaming decoder was producing text that was 56% wrong. The metrics measured whether the output was stable, not whether it was right. The single most valuable habit to take from today: for any decode path that departs from how the model was prompted in training, there must be a lane that scores its output against references before it ships. Everything else in this document is detail.

2. Mental model: how Qwen3-ASR turns audio into text

Qwen3-ASR is an encoder-decoder model. Audio goes in one side as a spectrogram, text comes out the other as tokens. Everything that happened today lives somewhere on this diagram.

Terms you need for the rest of this document

Mel spectrogram, frame, hop
Audio is sliced into overlapping 25 ms windows every 10 ms (the hop). Each window becomes 128 numbers (mel bins) describing energy per frequency band on a perceptual scale. One column is a frame; 100 frames is one second.
Chunk (encoder sense)
Qwen3-ASR's encoder processes mel in 100-frame (1 s) chunks independently through the conv stem, then attends across chunks in windows. A 253-frame clip is two full chunks plus a 53-frame tail. Do not confuse with the 30 s chunks the pipeline uses to split long files, or the 2 s chunks in streaming.
Conv stem, stride, receptive field
Three convolutions with kernel 3 and stride 2 each halve the time axis: 100 frames become 13 tokens. Each output token "sees" a receptive field of input frames wider than its own position, which is why padding decisions at the edge change the last token (section 4).
Decoder, prompt, greedy decoding
The decoder is a Qwen3 language model. It is given a chat-style prompt in which the audio vectors are spliced in where <|audio_pad|> tokens sit, and it writes language English<asr_text>the transcript one token at a time, always taking the most probable next token (greedy). It stops at an end-of-sequence token.
KV cache
Attention recomputes over every earlier token. The cache stores each earlier token's key and value vectors so generating token 200 costs one step, not 200. Prefill is the batch pass that fills the cache from the prompt.
WER, CER, primary error
Word error rate: (substitutions + insertions + deletions) / reference words, after normalising case and punctuation. Character error rate is the same on characters. For languages without spaces (Chinese, Japanese) WER on whitespace tokens is meaningless, so this project reports a primary error: WER for spaced languages, CER for the others.
RTF
Real-time factor: processing time divided by audio duration. 0.1 means one second of audio takes 100 ms. Below 1.0 is the bar for anything called real-time.
fp16, bf16, fp32
Three float formats. fp32 is 32 bits. fp16 and bf16 are both 16 bits but split them differently: fp16 has more precision and a small range (max 65504), bf16 has fp32's range and less precision. Apple's Metal path is fastest in fp16. Mixing them has a rule you need to know (section 3).
Quantization, group size, scales
Storing weights as 4- or 8-bit integers plus a small float scale and bias per group of 64 weights, so the original value is approximately int * scale + bias. Smaller groups: more accurate, more overhead. Section 7.

3. Silent float32 promotion (#20)

What the contributor found. The mlx-community quantized checkpoints store their non-integer tensors (scales, biases, norm weights, the unquantized audio tower) as bf16. The loader skipped its dtype cast for quantized checkpoints, so those tensors stayed bf16 while every activation entering the model was fp16.

The concept: type promotion. When an array library multiplies an fp16 tensor by a bf16 tensor it has to pick an output type, and neither can represent the other (fp16 lacks bf16's range, bf16 lacks fp16's precision), so MLX promotes to the common supertype: fp32. That one promotion propagates: the encoder output is fp32, so the decoder runs in fp32, so the KV cache is fp32. Nothing errors. Output text is identical. You pay twice the memory bandwidth and lose the fp16 fast paths.

How I verified it rather than trusting the PR: loaded mlx-community/Qwen3-ASR-0.6B-4bit on the newest MLX (0.32.2) with and without the fix. Parameter dtypes: 810 bf16 tensors became fp16, 198 uint32 packed weights unchanged. Same transcript. Warm latency 0.226 s to 0.154 s. Peak allocation 1.99 GiB to 1.47 GiB. The contributor's 1.7B numbers (15-30% faster, ~0.74 GiB) are consistent with that.

What to pay attention to

"Silently" is the dangerous word. This bug produced correct text for months. The only symptoms were latency and memory, which vary with machine load and are easy to attribute to something else. Two defences now exist: the regression test asserts the dtype of the encoder output, logits and cache after loading a bf16 quantized fixture; and ARCHITECTURE.md now names the rule. A third, worth adding, is a one-line --verbose print of the activation dtype at load.

4. Encoder tail padding (#21)

What the contributor found. When a clip is, say, 253 frames (2 full 100-frame chunks and a 53-frame tail), the official PyTorch encoder pads the tail to 100 frames before the conv stem and then keeps only the first ceil(53/8) = 7 output tokens. The MLX port convolved the 53-frame tail at its own width. Those are not the same computation.

The concept: convolutions with bias are not padding-invariant. Each conv layer has kernel 3, stride 2, padding 1. At the right edge, the last output of layer 1 reads frames 51, 52 and one padded zero either way. But layer 1 also has a bias and a GELU. In the padded version there are extra layer-1 outputs beyond the valid region whose value is GELU(bias), not zero, because the input to them is zero but the bias is not. Layer 2's last valid output then reads those non-zero positions. In the unpadded version they do not exist, so layer 2 sees zeros there. The last valid token of layer 3 inherits the difference.

A subtlety worth knowing. There are two "official" implementations and they disagree on sub-chunk inputs. The qwen_asr package (which this project's parity lane uses) applies pad_sequence across a sample's chunks, so a clip shorter than 100 frames is not padded. The HuggingFace transformers port always pads the mel axis to a multiple of 100 in the feature extractor. #21 follows qwen_asr. If a future parity run is done against transformers instead, sub-second clips will differ and it will not be a bug.

5. How to judge a numerics change

#21 changes numbers, so "does the transcript still match?" is the natural question, and it is the wrong one to ask first. Here is what the layers of evidence looked like and why the order matters.

MeasurementResultWhat it can and cannot tell you
LibriSpeech test-clean, 100 clips, WER before/after2.331% to 2.331%, 0/100 hypotheses changedGood: no regression. Cannot say whether the change helped, because greedy decoding is robust to small perturbations most of the time.
Multilingual-100 token match vs PyTorch66% to 64%Looks like a regression. Isn't: 6 MLX outputs changed (2 diverged, 1 converged, 3 mismatched either way) and 2 reference outputs changed because the PyTorch stack itself moved from torch 2.10 to 2.14. Greedy token match flips on borderline fp16 decisions in both directions.
Encoder output MAE vs fp32 PyTorch, last tail token, 20 clips0.0101 to 0.0046Decisive. Lower on 15 clips, unchanged on 4 (no tail or already at parity), higher on 1. This is the measurement closest to the change, before greedy decoding gets a chance to hide or amplify it.

Lesson

Measure as close to the change as you can. Downstream metrics answer "did it break anything?"; only the local measurement answers "did it do what it claims?". And always write down the reference stack (package, torch and transformers versions) next to parity numbers: two of the hundred references changed under us today with no code change on our side.

How the isolation was done, because the technique is reusable: a git worktree at the pre-#21 commit, the same MLX version, the same six clips, run with PYTHONPATH pointing at the worktree. All six changes reproduced, so they were #21's and not the MLX upgrade's. That experiment is what exposed the script import trap in section 8.

6. Streaming: the important finding (#26)

The roadmap's oldest open item was "run the streaming lane on real manifests and commit the artifacts". Doing that, and scoring the final text against references rather than only reporting stability metrics, showed that streaming was producing text that was more than half wrong.

LaneOfflineStreaming before (#26)Streaming afterAfter RTF
Multilingual-100 (5-20 s clips), primary error9.5%56.0%11.4%0.08
Long-form 10 x 75 s, primary error10.6%34.7%12.3%0.18

What the failures looked like, from one 13-second English clip:

REF : Four skiers in the women's sitting group failed to finish their runs, and 45 of the 117 total
      skiers in the Giant Slalom failed to rank in the race.
OLD : Force gears. In the woman's sitting group, failed to finish the. Runs and forty-five of the one
      hundred. In the woman's sitting group, failed to finish the. Failed to rank in the race.
NEW : Four skiers in the women's sitting group failed to finish their runs, and 45 of the 117 total
      skiers in the Giant Slalom failed to rank in the race.

Duplicated segments, dropped content, and a full stop at every 2 s chunk boundary. Chunk size 2, 4 and 8 s gave 49%, 28% and 24% on the same 30 clips. The floor stayed far above offline, so the loss was structural, not a granularity setting.

The concept: prompt shape must match training

The previous design was clever and fast. Each 2 s chunk was encoded on its own and appended to the decoder as a new chat turn, reusing the KV cache from earlier turns so cost stayed linear in session length. The problem is that the model was trained on exactly one prompt shape: one user turn containing all of the audio, one assistant turn containing all of the text. It has never seen "here is two more seconds, continue". It does its best, which is to treat each chunk as a fresh utterance, hence the full stops and the repeats.

Why the "prefix rollback" matters

If you simply re-transcribed the growing window each time, the text could change anywhere on every step, and a live caption would flicker. Forcing the previous output (minus its last K tokens) into the prompt as if the model had already written it does two things: the model continues from it rather than restarting, and only the last K tokens can legitimately change. That is where the project's stable_text comes from. One detail the official code handles and the port now does too: if cutting K tokens lands inside a multi-byte character (common in CJK), the decoded prefix contains U+FFFD, and you back off one more token until it does not.

Why the metrics did not catch it

partial_stability measures how much of the text is marked stable. rewrite_rate measures how often a new partial fails to extend the previous one. finalization_delta_chars measures how much text the final pass adds. All three describe the shape of the output over time. None compares it to what was said. A decoder that emits confident, stable, wrong sentences scores perfectly. The lane now stores a quality_vs_reference block (WER, CER, primary error of final_text), and the strict gate's rewrite_rate default moved from 0.30 to 0.85 because the new recipe regenerates its tail tokens every chunk by design (~0.65) and that is not a defect.

Cost and what remains

RTF went from 0.07 to 0.08 on short clips and 0.06 to 0.18 on 75 s clips, since a full 30 s window is re-encoded every 2 s. Still well under real time on an M4 Pro. The encoder processes each 100-frame chunk independently through the conv stem, so caching those per-chunk conv outputs across re-decodes is a clean optimisation that would take the encoder cost back to near-linear; it is the top streaming follow-up in EVAL_GAPS.md. The remaining ~2pp gap to offline is expected: the model decodes the first chunks with almost no right context, and the official implementation has the same gap.

7. Quantization: what to quantize, and how much

The concept. A 4-bit affine quantization stores each weight as an integer 0-15 and, per group of 64 weights, one fp16 scale and one fp16 bias: w ~ q * scale + bias. The storage cost is 4 bits per weight plus 32 bits per 64 weights of overhead (0.5 bit/weight), so about 4.5 bits per weight against 16 for fp16. 8-bit is the same scheme with 256 levels and about 8.5 bits per weight. Matrix multiplies run directly on the packed integers, which is where the speedup comes from: less memory to move.

The question is never "4 or 8". It is "which layers tolerate 4". The first build quantized everything at 4 bits and lost 0.3pp WER on 0.6B with 28 of 100 hypotheses changing, mostly proper nouns. Not a disaster, not a "high yes" either. So I swept:

0.6B recipeWERCERSizeHyps changed vs fp16
fp16 (reference)2.33%0.59%1.8 GB0
all 4-bit, group 642.63%0.93%430 MB28
all 4-bit, group 322.55%0.79%477 MB22
decoder 4-bit, encoder fp162.37%0.71%680 MB17
decoder 4-bit, encoder 8-bit (published)2.37%0.71%517 MB17
decoder 4-bit, encoder 8-bit, embeddings 8-bit2.37%0.75%591 MB17
all 8-bit, group 642.33%0.59%801 MB0

Reading the table. Almost all of the 4-bit loss came from the audio encoder. That is not surprising in hindsight: the encoder is a small stack of dense layers whose outputs feed everything downstream, and ASR encoders are known to be more quantization-sensitive than language-model decoders, which have redundancy across many layers and a softmax that forgives small logit errors. Halving the group size (a common first instinct) bought less than moving the encoder to 8 bits, and the encoder move costs only 90 MB because the encoder is a small fraction of the parameters. Quantizing the embedding table at 8 bits, another common intuition, changed nothing here.

What it needed in code. The loader had applied one (bits, group_size) to every quantized module. Now it reads each module's width from the shapes of its packed tensors (bits = packed_cols * 32 / in_features, group = in_features / scale_cols) and quantizes each group of modules separately. That also makes the loader robust to mixed-precision community checkpoints, which exist. Artifacts also drop the tied lm_head (a copy of the embedding matrix) and the loader rebuilds it.

The publication bar that ended up mattering

Not the WER number alone. Three things made these artifacts defensible: a hypothesis-level diff against the committed fp16 rows (so "28 differ" is a fact, not an impression), the baseline file named in the artifact (I initially compared the 0.6B 4-bit build against the previous 4-bit run instead of fp16, which a review bot caught), and a reproduce command pinned to a release tag on the model card.

8. Process lessons

Scripts imported the wrong checkout

With an editable install, python scripts/foo.py resolves mlx_qwen3_asr through the install's path hook, i.e. the checkout that was pip install -e'd, not the one the script sits in. Run from a git worktree, an "after" measurement was silently measuring "before". Caught because the delta was exactly zero, which was implausible. Every script now starts with a guarded import _repo_path. Habit: print mlx_qwen3_asr.__file__ before trusting any before/after number.

Review bots earned their keep

Every PR today drew Greptile or CodeRabbit findings, and every one was valid: a log line that misreported dtype, a clip count I had wrong (17 vs 15), a model card comparing against the wrong baseline, stale README bullets, an explicit max_new_tokens being treated as a floor, tensors not released per streaming step, unsupported bit widths silently accepted. None were deep; all were the kind of thing a tired author misses. Keep them on.

git commit -a in a shared tree

One fix commit used -a and swept your uncommitted memory note into a PR. Recovered by committing the research doc it cited, but the rule is now in operating memory: stage explicit paths.

The hung upload

A 1.2 GB HuggingFace upload sat at 0% CPU for an hour. It had already pushed the LFS blob; only the commit had not landed. Killing and re-running finished in seconds. Check the process before assuming a transfer must restart.

9. My views: what to pay attention to next

  1. Build the reference-scored streaming gate before anything else in streaming. Fold quality_vs_reference into eval_streaming_manifest.py and give the strict release gate a ceiling relative to the offline artifact (say, offline primary error + 3pp). This is the guard that was missing. It is a day of work and it prevents the class of failure that was live for months.
  2. Encoder-output caching in streaming. The conv stem is per-100-frame-chunk and the attention windows are fixed, so most of a 30 s window's encoder work is identical between consecutive re-decodes. Caching it would take long-form streaming RTF from 0.18 back toward 0.06 without touching correctness. Worth doing, but only after item 1 exists, because it is exactly the kind of optimisation that can subtly break parity.
  3. Treat the audio encoder as the sensitive component. Today it was the source of the tail-padding divergence and of the 4-bit quality loss. When a future change touches it, the encoder-output MAE against fp32 PyTorch (the script pattern from section 5) is the cheapest decisive test you have.
  4. The aligner is the next un-audited surface. The forced aligner has its own encoder path and its own parity numbers from February. Nothing today touched it, which also means nothing today verified it against the newest MLX or the tail-padding fix. The same "run the real lane and score against references" exercise is due there.
  5. Publish from CI, not a laptop. The quantized artifacts went up from this machine. Add HF_TOKEN to the repo secrets so publish-quantized.yml can run, and re-publish whenever the recipe or the loader changes. The cards pin v0.4.3; keep that honest.
  6. Watch the reference stack. Two of one hundred PyTorch reference outputs changed between torch 2.10 and 2.14 with no change on our side. Parity numbers are only comparable when the stack is recorded, which the artifacts now do. Consider pinning the parity venv.
  7. Be skeptical of clever. The incremental KV streaming design was the most technically interesting thing in the repo and the least correct. The official recipe is dull and right. When a port departs from the reference algorithm for speed, the burden of proof is a reference-scored lane, not a stability metric.

10. Glossary

Affine quantization
Representing a weight as q * scale + bias with a small integer q; "affine" because of the additive bias term (symmetric schemes omit it).
Autoregressive decoding
Generating one token at a time, feeding each back in as input for the next.
bf16 / fp16 / fp32
See section 3. Mixing bf16 and fp16 promotes to fp32.
CER / WER / primary error
Character / word error rate; primary picks the appropriate one per language.
Chunk
Overloaded: 100-frame encoder chunk (1 s), 30 s long-audio chunk, 2 s streaming chunk. Always ask which.
Endpointing
Choosing where to cut audio for a decode step. fixed cuts every N seconds; energy looks for a low-energy (silence-like) point near the boundary.
EOS
End-of-sequence token; the decoder emits it to stop. Runaway decodes that never emit it are bounded by max_new_tokens and a repetition detector.
GELU
A smooth activation function used after each conv layer here. GELU(0) = 0 but GELU(bias) is not, which is the crux of section 4.
GQA
Grouped-query attention: several query heads share one key/value head, shrinking the KV cache.
Greedy
Always pick the highest-probability next token. Deterministic, which is what makes token-level parity comparisons possible at all.
Group size
How many weights share one scale/bias pair in quantization. 64 here.
Hypothesis
The model's output transcript for a clip, as opposed to the reference (ground truth).
KV cache / prefill
Stored attention keys and values for earlier tokens; prefill fills it from the prompt in one pass.
LibriSpeech test-clean / test-other, FLEURS
Standard evaluation sets. LibriSpeech is English audiobooks (clean = easy speakers, other = harder). FLEURS is read speech in 100+ languages; the multilingual-100 manifest samples 10 clips from each of 10 languages.
Mel filterbank
The set of triangular filters that map FFT bins to perceptual mel bins. Loaded from assets/mel_filters.npz.
MRoPE
Multi-dimensional rotary position embedding; Qwen3-ASR interleaves three position streams (sections 24/20/20). One of the "silently wrong if broken" invariants in CLAUDE.md.
pad_sequence
PyTorch utility that right-pads a list of tensors to the longest one. In the official encoder it pads a sample's chunks to 100 frames.
Parity
Agreement between this implementation and the official PyTorch one, measured at the token level (exact match) or at the tensor level (mean absolute error).
Prefix rollback
Streaming technique: force the previous output minus its last K tokens into the prompt so the model continues rather than restarts. K = unfixed_token_num.
Receptive field
The span of input positions that influence one output position of a convolution stack.
RTF
Real-time factor; processing time / audio duration.
Speaker round-robin
The sampling used for the 100-clip LibriSpeech lane: cycle through speakers so no one voice dominates. Deterministic, so runs are comparable.
Tied embeddings
The output projection (lm_head) reuses the input embedding matrix. Both Qwen3-ASR sizes do this.
Windowed attention
The audio encoder attends only within fixed-size windows of tokens (block-diagonal mask), which is why chunks can be processed and cached independently.
