# Implementation Memory - 2026-09

## MEM-2026-09-06-001

- Date: 2026-09-06
- Scope: Issue #16 / PR #18. Server inference failed on MLX 0.31+ with
  `There is no Stream(gpu, 1) in current thread`.
- Decision:
  - Root cause is library-level, not server-level: init-time buffers that are
    not parameters (`SinusoidalPositionEmbedding._pe`,
    `InterleavedMRoPE._inv_freq`) were lazy graphs bound to the constructing
    thread. Materialize them with `mx.eval` in `__init__`.
  - Keep PR #18's dedicated single-worker executor in the server as defence in
    depth, with `try/finally` cleanup and `shutdown(wait=True)` off the loop.
- Reuse next time:
  - Bisect thread-affinity failures op by op on a worker thread; `nn.Linear`
    weights and `mx.load` tensors are portable, only unevaluated graphs are
    not. `mx.eval(model.parameters())` does not reach underscore attributes.
  - Build test inputs inside the worker thread; otherwise `mx.zeros` created
    on the test thread reproduces the bug for the wrong reason.
  - Keep a second venv with the newest MLX; the repo venv (0.30.6) hides
    every thread-affinity bug and the newer `as_strided` error.
- What did not work:
  - `mx.synchronize()` or `mx.set_default_stream(...)` on the worker thread.
  - Evaluating `model.parameters()` alone.
- Evidence:
  - Probe matrix on MLX 0.32.2: load main/infer worker FAIL; load worker A /
    infer worker B FAIL; load+infer same thread OK; after buffer eval all OK.
  - `tests/test_model.py::TestThreadPortability` fails on MLX 0.32.2 without
    the fix and passes with it; passes on 0.30.6 either way.
  - `mlx_qwen3_asr/encoder.py`, `mlx_qwen3_asr/mrope.py`,
    `mlx_qwen3_asr/server.py`

## MEM-2026-09-19-016

- Date: 2026-09-19
- Scope: Handoff item 3, streaming prefix reuse (Decision 30).
- Decision:
  - Cache encoder output and decoder KV for complete 800-frame attention
    windows of the live streaming window, keyed on the log-mel global max;
    reset on window commit. Each chunk: one `encode_frames` over uncached
    frames (new blocks + tail), one prefill of the prompt tail + text prefix
    on `KVCache.fork()`, generate, then trim the fork to the block boundary
    and adopt it as the prefix KV. `reuse_window_prefix=True` default on
    `init_streaming` / `Session.init_streaming`; `--no-reuse-window-prefix`
    on `eval_streaming_manifest.py`.
  - A block is complete only when a frame follows it (last STFT frame reaches
    200 samples past the block end). `n_complete = (n_frames - 1) // 800`.
  - `KVCache.fork()` shares arrays in concat mode, copies in preallocated
    mode: MLX `a[i:j] = v` is visible through every reference.
- Reuse next time:
  - Stage profile first (mel 1 / encoder 18 / prefill 31 / generation 50%).
    The roadmap premise (encoder dominates) was wrong; encoder-only caching
    would have capped at ~13%.
  - First cut (separate block encode + separate KV-extension prefill) was
    1.18x on 80 s clips but 12% slower on 10-20 s clips: fixed launch cost
    per extra call beat the saved compute. Folding into the calls that happen
    anyway fixed both lanes. Count calls per chunk, not FLOPs.
  - Exactness probes before building: mel frames of complete blocks are
    bit-identical while the global max holds; two-stage prefill is
    bit-identical to one pass (logits and KV); block-wise encode differs by
    reduction order (max 1.6e-6 on scale 1e-2). Expect a few hypothesis flips
    and score them, do not assume zero.
  - Bug caught by the fake-tower test: `cached_tokens` already included the
    blocks appended this chunk, so audio tokens were double-counted in the
    prompt. Doubles carrying `encode_frames` / `get_output_lengths` with real
    signatures made the arithmetic testable without a model.
